## What changed

The panel's boolean `open` became a 4-value `PanelState = "closed" | "open" | "docked" | "peek"`.
The component now only unmounts (`return null`) when `state === "closed"`; docked/peek keep the
same `.cd-chat-panel` DOM node mounted (composer input, `messages`, `conversationId`, queued
prompts all survive), and a small `.cd-chat-dock` pill mounts/unmounts alongside it.

GSAP owns the transform/opacity/pointer-events choreography between states. Per the repo's
GSAP idiom (matches `AutopilotHero.tsx`): `gsap.registerPlugin(useGSAP)` at module scope,
`useGSAP({ scope: containerRef })` to get a `contextSafe`, and — after a first code-review
pass flagged five near-duplicate hand-written transition functions recreated on every render —
a single `contextSafe`-wrapped executor (`runTransitionRef`, lazily built once via a
ref-null-check instead of on every keystroke) driven by two data tables, `PANEL_TARGET` and
`PILL_TARGET`, keyed by target state. Reduced motion uses the dashboard's existing shared
predicate, `reduced()` from `hero/hero-motion.ts` ("the single prefers-reduced-motion predicate
for dashboard motion"), not a second private mechanism — swaps every tween for an instant
`gsap.set` to the same end state.

## State-machine walkthrough

| From | Event | To | Animation |
|---|---|---|---|
| closed | sidebar/⌘K bump `openSignal`, or a Home prompt hand-off | open | Panel mounts fresh; existing CSS `cd-chat-panel-in` drawer-slide plays (unchanged from before this PR). A `gsap.set` baseline (xPercent 0/scale 1/opacity 1/pointerEvents auto) runs alongside so later dock/peek tweens have a correct starting point without fighting that CSS keyframe. |
| open | merchant navigates (app.nav.screen changes) | docked | `dockFromOpen`-equivalent: panel tweens to translateX(100%)/scale .9/opacity 0/pointerEvents none (.38s power2.inOut); pill mounts and gets a **one-time** attention pulse (overshoot to scale 1.08 then settle) — not a loop. `gsap.killTweensOf(pill)` guards a rapid re-dock from stacking a second pulse. |
| open | merchant clicks the X, or a DraftActionCard action closes it | closed | Instant unmount, no exit tween — unchanged pre-existing behavior. |
| docked | hover (mouseenter on the container wrapping pill+panel) | peek | Panel tweens to translateX(50%)/scale 1/opacity 1/pointerEvents none (.35s power3.out) — shows the left half of the panel (header + start of thread) with the right half sliding past the viewport edge. Pill fades out. |
| docked | click the pill | open | Panel tweens back to full open (translateX 0, pointerEvents auto). Focus is *not* force-set here (only the dedicated "opened" autofocus effect handles that, gated on `state === "open"`). |
| peek | mouse leaves (mouseleave on the container) | docked | Panel tweens back to docked end-state (no pulse this time — pulse is reserved for the real "just left the page" moment, not a hover bounce-back); pill fades back in. |
| peek | click anywhere on the preview (a full-cover `.cd-chat-peek-catch` button, nested inside the panel so it shares its fixed box) | open | Same open tween as docked→open. |
| **any state** | X button (only rendered in the full `open` header) | closed | Instant unmount. |
| **docked / peek / closed** | merchant navigates to another screen | *(no change)* | Explicitly a no-op per spec — only a genuinely open panel needs to get out of the way. |
| **any state including docked/peek/closed** | a prompt is handed off from Home's prompt bar | open | Always reopens fully — the merchant explicitly sent a prompt, so it must not stay hidden. Queued-prompt draining resumes once `state === "open"` and history has loaded. |

### Edge cases
- **Screen change during peek**: no-op, per spec (only `open` docks). Peek stays peek until hover leaves or it's clicked.
- **Close during peek**: there's no X on the pill/peek preview by design — the only literal close affordance lives in the full-open header. To fully close from peek, click through to open, then X. Documented limitation, not a bug: `close()`'s only current callers are inside the open header and DraftActionCard, both only reachable once open.
- **Rapid hover on/off**: `enterDockZone`/`leaveDockZone` are plain functional `setState` toggles; GSAP tweens use `overwrite: "auto"` so a reversed tween cleanly interrupts the in-flight one instead of queuing.
- **Prompt hand-off while docked/peek**: reopens fully (explicit design decision per the task brief — an explicit send always wins over a minimized state).
- **History fetch in flight while docking**: gated by a `historyFetchStartedRef` (not just `!historyLoaded`) so a state change mid-fetch (e.g. open→docked before the response lands) can't refire `fetchAssistantHistory()`.
- **Docking while the composer has focus**: the docking transition blurs any focused descendant of the panel first, so keystrokes can't silently land in a now-hidden, `aria-hidden` composer.

## Mobile
No dock on the phone breakpoint (`max-width: 767px`, matching the codebase's existing mobile
cutover): the nav-change effect checks `window.matchMedia` and no-ops there, since
`.cd-chat-panel` is already effectively full-screen at that width (existing `max-width:
calc(100vw - 32px)` rule) — there's no edge to collapse into. Documented as the simplest
correct behavior per the task brief's mobile carve-out.

## Concerns / follow-ups (not blockers)
- The mobile-breakpoint check (`window.matchMedia("(max-width: 767px)")`) is a one-shot read
  on navigation, not a subscribed listener — a resize/rotate across the breakpoint without an
  accompanying navigation could leave the dock behavior one step behind the CSS's live media
  query. Low severity (docking only ever fires on an actual screen change).
- No literal close (X) affordance from docked/peek states — by design, but worth confirming
  with the merchant-facing owner that "reopen, then X" is acceptable rather than adding a
  close control to the pill itself.
- `docFromOpen`/dock end-state duration/ease (0.38s power2.inOut) was normalized to a single
  value shared by both open→docked and peek→docked (previously two slightly different
  hand-tuned values); a design pass may want to re-tune if the merged timing feels off.

## Fix pass — review findings (2026-07-09/10)

Fixed three review findings on this feature.

### Finding 1 (Critical) + Finding 2 (Important) — same root cause, same fix
While docked/peek, the panel subtree was visually hidden (opacity/pointer-events via GSAP,
plus `aria-hidden`) but every control inside stayed keyboard-focusable and Enter-activatable —
Tab could reach a `PendingConfirmCard`'s invisible "Confirm" button and Enter would fire a real
action (e.g. a refund). Pairing `aria-hidden` with focusable descendants is also a standalone
WCAG 4.1.2 violation.

Fix: dropped `aria-hidden={state !== "open"}` from the panel root and added
`panelRef.current?.toggleAttribute("inert", state !== "open")` in a `useEffect` keyed on
`state`. `inert` removes the whole subtree from both the tab order and the accessibility tree,
so it fixes both findings at once with no separate `aria-hidden` needed.

Not done as the `inert` JSX prop: the installed `@types/react` (18.3.28, pinned per this repo's
React 18 cap) only declares `inert` in `experimental.d.ts`, not the stable `index.d.ts` this
project's types resolve to — the prop doesn't exist on `HTMLAttributes` and fails to typecheck.
Used the ref/`toggleAttribute` fallback the finding called out for exactly this case. `tsc
--noEmit` is clean with it.

One structural consequence: the `peek` state's full-cover click-to-open control
(`.cd-chat-peek-catch`) used to be nested inside the panel, relying on an explicit
`pointer-events: auto` override to stay clickable through the panel's own
`pointer-events: none`. If left nested, `inert` on the panel would also have disabled *that*
button, silently breaking "click anywhere on the peek preview to open" (a real, intentional
product affordance, not part of what needed hiding). Moved it to be a sibling of the panel
(still inside the same container, still visually overlaying it via matching `position: fixed`
coordinates in CSS) so it sits outside the inert subtree and keeps working. Marked it
`aria-hidden="true" tabIndex={-1}` explicitly, since it's mouse-only by design — the dock pill
remains the sole keyboard/AT-accessible way to reopen from peek, per the original comment's
intent.

Verified: with `state !== "open"`, `panelRef.current` has the `inert` attribute (DOM
`toggleAttribute` result), so `document.activeElement` can never land inside it via Tab, and
the `PendingConfirmCard`'s "Confirm" button cannot be Enter-fired while hidden. With
`state === "open"`, the effect runs `toggleAttribute("inert", false)`, removing the attribute
entirely — the panel is fully interactive, matching pre-fix behavior.

### Finding 3 — no close affordance from docked state
The docked pill had no dismiss control (previously documented as a known limitation: reopen,
then hit the header X). Added a small `×` button *on* the pill: `.cd-chat-dock-wrap` now wraps
the existing `.cd-chat-dock` pill and a new `.cd-chat-dock-dismiss` button (siblings — a
`<button>` can't validly nest another interactive element). The `×` is positioned at the pill's
top-right corner via `position: absolute` inside the wrap, `aria-label="Dismiss assistant"`,
scaled down from `.cd-chat-close`'s look (18px circle vs. 28px, same `--gray-bg`/`--text-2`
tokens and hover-darken transition). It's revealed on `.cd-chat-dock-wrap:hover` or its own
`:focus-visible` (plain CSS opacity transition, no GSAP needed here — matches the brief's "CSS
is fine"). Being a real `<button>`, it's in the tab order regardless of its current opacity, so
a merchant who tabs onto the pill can Tab once more onto the `×` and activate it with the
keyboard even before the hover-reveal triggers.

`onClick` calls `e.stopPropagation()` before `setState("closed")`. Structurally the `×` is a
sibling of the pill, not a descendant, so the click wouldn't reach the pill's own `onClick`
via bubbling regardless — the `stopPropagation()` is defensive, guarding against a future
refactor that nests them, and costs nothing today.

Verified: clicking the `×` sets `state` straight to `"closed"` (panel unmounts, pill unmounts)
without ever calling `openFull`/`setState("open")` — confirmed by reading the handler in
isolation from the pill's own `onClick={openFull}`, which is a separate button with no shared
event path.
